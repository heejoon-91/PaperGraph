# gstack 스킬 역할 정리

이 문서는 현재 환경에 설치된 gstack 계열 스킬이 어떤 상황에서 쓰이는지 정리한다.

스킬 이름은 보통 `gstack-...` 형태로 설치되어 있지만, 대화에서는 `/health`, `/investigate`, `/review`처럼 짧은 이름으로 부를 수 있다. 같은 역할의 중복 경로가 있을 수 있으나, 역할은 동일하게 보면 된다.

## 빠른 선택 가이드

| 상황 | 먼저 쓸 스킬 | 역할 |
| --- | --- | --- |
| 프로젝트가 만들 가치가 있는지, 누구를 위한 것인지 다시 보고 싶다 | `office-hours` | YC office hours처럼 수요, 사용자, 좁은 시작점, 다음 검증 행동을 압박해서 찾는다. |
| 프로젝트 방향성을 더 크게 보거나 줄여야 하는지 판단하고 싶다 | `plan-ceo-review` | founder/CEO 관점에서 문제 정의, scope, 10점짜리 제품 가능성, 전략 리스크를 검토한다. |
| 방향성, 설계, 디자인, 개발자 경험을 한 번에 자동 검토하고 싶다 | `autoplan` | CEO, design, engineering, DX 리뷰를 순서대로 돌려 실행 가능한 계획으로 정리한다. |
| 코드베이스 현재 상태를 점수화하고 싶다 | `health` | 테스트, 타입체크, 린트 등 사용 가능한 품질 도구를 돌려 상태판을 만든다. |
| 버그, 실패, 에러 원인을 찾고 싶다 | `investigate` | 재현, 원인 추적, 가설 검증, 수정, 회귀 테스트까지 진행한다. |
| 변경사항을 머지 전에 점검하고 싶다 | `review` | diff를 기준으로 결함, 위험, 빠진 테스트, 문서 불일치를 찾는다. |
| 웹 앱을 실제로 눌러보며 검증하고 싶다 | `qa` | 브라우저로 사용자 플로우를 테스트하고 발견한 버그를 고친다. |
| 버그 리포트만 받고 싶다 | `qa-only` | 코드는 고치지 않고 QA 결과와 재현 절차만 만든다. |
| PR을 만들고 배포 준비를 하고 싶다 | `ship` | 테스트, 리뷰, 변경 기록, 커밋, 푸시, PR 생성 흐름을 진행한다. |
| PR을 머지하고 배포 상태를 확인하고 싶다 | `land-and-deploy` | 머지, CI 대기, 배포 확인, 운영 상태 점검을 진행한다. |
| 개발 중간 상태를 저장하고 싶다 | `checkpoint` | 현재 git 상태, 결정사항, 남은 일을 저장해 이어서 작업할 수 있게 한다. |
| 설계나 아키텍처를 검토하고 싶다 | `plan-eng-review` | 데이터 흐름, 모듈 경계, 테스트 전략, 성능 리스크를 검토한다. |
| 제품 범위나 전략을 다시 보고 싶다 | `plan-ceo-review` | 범위 확장/축소, 사용자 가치, 더 큰 제품 가능성을 검토한다. |

## 프로젝트 운영 스킬

| 스킬 | 역할 | 쓰는 시점 |
| --- | --- | --- |
| `gstack` | gstack의 기본 브라우저/QA 실행 기반이다. | 사이트를 열어 테스트하거나 브라우저 자동화가 필요할 때. |
| `autoplan` | CEO, 디자인, 엔지니어링, DX 리뷰를 자동으로 묶어 실행한다. | 큰 기능 계획을 한 번에 검토하고 싶을 때. |
| `health` | 품질 대시보드를 만든다. | 개발 시작 전, PR 전, 리팩터링 후. |
| `investigate` | 원인 없는 수정을 금지하고, 버그의 실제 원인을 찾아 고친다. | 테스트 실패, import 실패, 500 에러, 이상 동작 발생 시. |
| `review` | 머지 전 diff 리뷰를 한다. | PR 전, 기능 완료 후. |
| `checkpoint` | 현재 작업 상태를 저장한다. | 세션 종료 전, 큰 리팩터링 전, 브랜치 전환 전. |
| `learn` | 이전 세션에서 저장한 학습 내용을 조회하고 관리한다. | 예전에 비슷한 문제를 해결했는지 확인할 때. |
| `retro` | 최근 개발 흐름을 회고한다. | 주간 회고, 스프린트 종료, 팀 리뷰. |
| `document-release` | 코드 변경에 맞춰 문서를 갱신한다. | 기능이 끝난 뒤 README, architecture, changelog를 맞출 때. |

## 개발, 리뷰, 안정화 스킬

| 스킬 | 역할 | 쓰는 시점 |
| --- | --- | --- |
| `qa` | 실제 브라우저에서 테스트하고 발견한 문제를 고친다. | 웹 UI, 폼, 인증, 업로드, 반응형 화면 검증. |
| `qa-only` | 수정 없이 QA 리포트만 만든다. | 코드 변경 전 버그 목록만 받고 싶을 때. |
| `benchmark` | 페이지 성능, 로딩 시간, Core Web Vitals, 리소스 크기를 측정한다. | 웹 앱 성능 기준선을 만들거나 회귀를 잡을 때. |
| `canary` | 배포 후 운영 페이지를 감시한다. | 배포 직후 화면 깨짐, 콘솔 에러, 성능 저하를 확인할 때. |
| `codex` | Codex CLI로 독립 리뷰, challenge, 상담을 수행한다. | 두 번째 모델 의견이 필요하거나 adversarial review가 필요할 때. |
| `cso` | 보안 감사와 위협 모델링을 한다. | secrets, dependency, CI/CD, OWASP, LLM 보안 점검. |
| `careful` | 위험 명령에 대한 안전 장치를 켠다. | 프로덕션, DB, 삭제, force push 같은 위험 작업 전. |
| `freeze` | 수정 가능 범위를 특정 디렉터리로 제한한다. | 디버깅 중 실수로 unrelated file을 건드리지 않게 할 때. |
| `unfreeze` | `freeze` 제한을 해제한다. | 작업 범위를 다시 넓혀야 할 때. |
| `guard` | `careful`과 `freeze`를 합친 강한 안전 모드다. | 운영 환경이나 공유 코드베이스를 만질 때. |

## 설계, 제품, 기획 스킬

이 그룹이 gstack의 "벤처회사 전문가 능력"에 가장 가깝다. 단순히 코드를 잘 짜는지가 아니라, 왜 이걸 만들고, 누구에게 절박하며, 어떤 작은 시작점으로 검증할지를 다룬다.

| 스킬 | 역할 | 쓰는 시점 |
| --- | --- | --- |
| `office-hours` | YC office hours처럼 아이디어의 수요 현실, 기존 대안, 절박한 사용자, 가장 좁은 wedge를 찾는다. | 프로젝트 방향이 아직 흐리거나, 만들 가치부터 검증해야 할 때. |
| `plan-ceo-review` | 제품 범위와 전략을 founder/CEO 관점에서 재검토한다. 10점짜리 제품 가능성, scope expansion/reduction, 사용자 가치의 크기를 본다. | 지금 계획이 충분히 야심찬지, 너무 넓은지, 더 좋은 방향이 있는지 볼 때. |
| `plan-eng-review` | 아키텍처와 실행 계획을 엔지니어링 관점에서 검토한다. | 구현 전 데이터 모델, 모듈 경계, 테스트 전략을 잠글 때. |
| `plan-design-review` | 디자인 계획을 시각, UX, 정보 구조 관점에서 검토한다. | UI 구현 전 화면 계획을 다듬을 때. |
| `plan-devex-review` | 개발자 경험을 검토한다. | API, SDK, CLI, 문서, 온보딩 흐름을 만들 때. |
| `plan-tune` | gstack이 묻는 질문의 빈도와 스타일을 조정한다. | 질문이 너무 많거나, 특정 질문을 자동 결정하게 하고 싶을 때. |

## 방향성 개선에 쓰는 스킬

| 스킬 | 벤처회사식 역할 | PaperGraph에 던지는 질문 |
| --- | --- | --- |
| `office-hours` | 투자자/창업 멘토가 아이디어의 수요 현실을 압박해서 확인하는 역할. | "누가 PaperGraph를 오늘 당장 써야 하는가?", "그 사람은 지금 어떤 불편한 대안으로 버티는가?", "논문 요약이 아니라 어떤 작업을 끝내주면 돈이나 시간이 절약되는가?" |
| `plan-ceo-review` | CEO가 제품 범위와 야심을 재설계하는 역할. | "PaperGraph는 단순 논문 요약기가 아니라 연구자의 지식 작업 시스템이 될 수 있는가?", "MVP를 어디까지 줄여야 빠르게 검증되는가?", "반대로 10점 제품이라면 어떤 경험이어야 하는가?" |
| `autoplan` | 여러 전문가 리뷰를 자동으로 묶는 파트너 미팅 역할. | "제품 방향, 아키텍처, 디자인, DX가 서로 맞물리는가?", "지금 구현 순서가 가장 빠른 검증 경로인가?" |
| `plan-devex-review` | 개발자 플랫폼/도구 전문가 역할. | "이걸 CLI나 라이브러리로 공개한다면 첫 성공까지 몇 분 걸리는가?", "샘플 PDF에서 graph JSON까지 가는 happy path가 충분히 짧은가?" |
| `plan-design-review` | 제품 디자이너/UX 리드 역할. | "그래프 시각화가 예쁜 그림이 아니라 연구자가 답을 찾는 도구인가?", "노드/엣지/근거 문장이 한 화면에서 이해되는가?" |

## 디자인, 프론트엔드, 브라우저 스킬

| 스킬 | 역할 | 쓰는 시점 |
| --- | --- | --- |
| `design-consultation` | 디자인 시스템과 브랜드 가이드를 만든다. | 새 UI 프로젝트를 시작하거나 `DESIGN.md`가 필요할 때. |
| `design-shotgun` | 여러 디자인 방향을 빠르게 생성하고 비교한다. | UI 방향을 아직 정하지 못했을 때. |
| `design-html` | 승인된 디자인을 HTML/CSS로 구현한다. | mockup이나 디자인 계획을 실제 페이지로 만들 때. |
| `design-review` | 실제 화면의 시각 품질을 감사하고 고친다. | spacing, hierarchy, responsive, visual polish가 필요할 때. |
| `browse` | headless browser로 페이지를 열고 상호작용한다. | 사이트 QA, 스크린샷, 폼 테스트, 상태 확인. |
| `open-gstack-browser` | 눈으로 볼 수 있는 GStack Browser를 연다. | 사용자가 브라우저 동작을 직접 보고 싶을 때. |
| `setup-browser-cookies` | 실제 브라우저 쿠키를 테스트 브라우저로 가져온다. | 로그인 필요한 페이지를 QA할 때. |
| `pair-agent` | 다른 AI agent에게 브라우저 접근 권한을 준다. | 원격 agent와 같은 브라우저 세션을 공유할 때. |

## 배포, 운영, 릴리스 스킬

| 스킬 | 역할 | 쓰는 시점 |
| --- | --- | --- |
| `ship` | PR 생성 전 과정을 진행한다. | 코드가 준비되어 PR을 만들고 싶을 때. |
| `land-and-deploy` | PR 머지와 배포 검증을 진행한다. | 승인된 PR을 운영으로 보낼 때. |
| `setup-deploy` | 배포 플랫폼과 health check 설정을 잡는다. | `land-and-deploy`를 자동화하기 전. |
| `canary` | 배포 후 운영 상태를 감시한다. | 배포 직후 회귀를 빠르게 잡을 때. |
| `benchmark` | 성능 기준선과 회귀를 측정한다. | 배포 전후 성능 변화를 확인할 때. |
| `gstack-upgrade` | gstack 자체를 최신 버전으로 업데이트한다. | 스킬 기능이 오래됐거나 최신 기능이 필요할 때. |

## PaperGraph에서 우선순위가 높은 스킬

현재 PaperGraph는 Python 라이브러리 형태라 브라우저 기반 스킬보다 코드 품질과 아키텍처 스킬이 먼저 맞다.

| 우선순위 | 스킬 | 이유 |
| --- | --- | --- |
| 1 | `office-hours` | PaperGraph가 누구의 절박한 문제를 푸는지 먼저 좁혀야 한다. 지금은 "논문 요약 + 그래프"라서 사용자가 아직 너무 넓다. |
| 2 | `plan-ceo-review` | 방향을 정한 뒤, MVP를 줄일지 키울지 founder 관점에서 결정해야 한다. |
| 3 | `plan-eng-review` | PDF parsing, extraction, graph model, QA가 커지기 전에 데이터 계약을 잠근다. |
| 4 | `health` | 테스트 실행 가능성, 린트/타입체크 도입 상태를 계속 측정해야 한다. |
| 5 | `investigate` | import, pytest cache, 데이터 무결성 같은 개발 환경 문제를 원인부터 잡는다. |
| 6 | `review` | 그래프 생성 로직이 조용히 잘못된 데이터를 만들지 않는지 PR 전 확인한다. |
| 7 | `document-release` | README와 architecture가 실제 코드 계약과 어긋나지 않게 유지한다. |
| 8 | `cso` | PDF 처리와 LLM 추출이 들어가면 파일 입력, prompt injection, dependency 보안 점검이 필요하다. |
| 9 | `checkpoint` | 작은 MVP에서 기능이 빠르게 늘어날 때 작업 상태를 잃지 않게 한다. |

UI나 웹 시각화가 들어가면 다음 스킬의 우선순위가 올라간다.

| 상황 | 스킬 |
| --- | --- |
| Cytoscape.js, pyvis viewer, 웹 UI 추가 | `design-review`, `qa`, `browse` |
| 배포 가능한 demo site 추가 | `setup-deploy`, `ship`, `land-and-deploy`, `canary` |
| 그래프 화면 성능 확인 | `benchmark` |
| 개발자용 API/CLI 공개 | `plan-devex-review`, `devex-review` |

## 추천 운영 루틴

### 기능 개발 시작 전

```text
office-hours -> plan-ceo-review -> plan-eng-review -> health -> checkpoint
```

먼저 사용자의 절박한 문제와 제품 방향을 좁히고, 그 다음 아키텍처 리스크와 품질 기준선을 잡는다.

### 기능 구현 중 버그 발생

```text
investigate -> health -> review
```

재현 가능한 원인을 찾고, 테스트로 고정한 뒤 diff를 검토한다.

### PR 전

```text
health -> review -> document-release -> ship
```

테스트, 코드 리뷰, 문서 동기화, PR 생성을 한 흐름으로 처리한다.

### 배포 가능한 웹 데모가 생긴 뒤

```text
qa -> benchmark -> ship -> land-and-deploy -> canary
```

사용자 플로우, 성능, 배포, 운영 감시까지 한 번에 본다.
